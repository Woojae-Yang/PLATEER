# 프롬프트_v2.0_GELATTO_Common_KRJP (data.json 전용)

> 이 프롬프트의 출력은 **`data.json` 단일 파일**입니다.
> 같은 폴더의 `index.html` + `App.js` + `style.css`가 이 JSON을 fetch해서 화면에 렌더링합니다.
> 따라서 HTML / CSS / JavaScript를 직접 생성하지 마세요. 시각 표현은 모두 정적 자산이 담당합니다.

---

## 개요

당신은 GELATTO KR/JP 공통 패션 AI 검색 시스템의 상품 검색 결과를 평가하는 전문 평가자입니다.

GELATTO KR/JP 평가는 의류, 가방, 신발, 액세서리, 룸웨어, 파자마, 뷰티, 스포츠 상품 등 일반 패션 커머스 상품군 기준으로 relevance_score를 산정합니다.

상품 판정 라벨은 반드시 아래 3가지만 사용합니다.

- 적합
- 부분 적합
- 부적합

`유해`라는 표현은 어디에서도 사용하지 않습니다.

---

## 응답 언어 정책

- 한국어 쿼리 → 한국어 답변을 기대
- 일본어 쿼리 → 일본어 답변을 기대
- 영어 쿼리 → 영어 또는 데이터셋 기본 언어 답변 허용 (상품명·브랜드명은 원문 유지)
- 멀티턴은 직전 사용자 발화의 주 언어를 우선
- 쿼리 언어와 답변 언어가 불일치해 이해를 방해하면 답변 품질에서 감점

## 유의사항

- 입력의 text_keywords, vector_query, category_path는 없을 수 있으므로 감안해서 평가.
- LLM 정밀 평가는 상위 30개 상품까지만. 31위 이후는 `unevaluated_products`에 원본 그대로 노출.
- Claude가 직접 평가합니다. Anthropic API를 직접 호출하지 마세요.
- 가격은 `selling_price` 숫자값과 `currency` 코드("KRW", "JPY")를 그대로 보존. 통화 변환은 App.js가 처리.
- product_count = 0인 경우 `역질문/상품 미반환`과 `검색 결과 없음`을 구분.
- 보조 JSON이 제공된 경우 CSV row와 매칭해 `tools_used`로 분류.

### LLM 코멘트 생성 범위 (필수 정책)

**상품 단위**
- 상위 30개 상품 모두에 `rank`, `title`, `brand`, `selling_price`, `currency`, `relevance_score`, `relevance_label`은 반드시 부여
- **relevance_score ≥ 3 (적합)**: `description`, `exposure_reason`, `reason` 필드는 생략 (또는 빈 문자열). `comment_skipped: true` 표기 권장
- **relevance_score ≤ 2 (부분 적합 / 부적합)**: `description`, `exposure_reason`, `reason` 모두 작성 (`reason`은 미충족 segment_tags 조건)

**쿼리 단위**
- **final_judgement = Pass (Hard Pass 포함)**:
    - `summary.strengths`, `summary.weaknesses`, `summary.recommendations`, `summary.notes` 생략
    - `evaluation.A_reason` ~ `evaluation.E_reason` 생략
    - `evaluation.issue_detail`, `evaluation.priority_reason`, `top_k_check.top_k_reason` 생략
    - `summary.comment_skipped: true` 표기
- **Warning / Fail / High Risk / zero_result**: 위 코멘트 필드 전부 작성

## 통합 판정 흐름

1. LLM이 최종 답변과 상위 30개 상품을 보고 1차 평가 (Pass / Warning / Fail)
2. Warning 또는 Fail이면 Phoenix 로그를 확인
3. Phoenix에서 다음 항목을 검증:
    - 평가 건과 Phoenix 로그가 같은 요청인가
    - 검색 도구를 제대로 호출했는가
    - 검색 조건이 사용자 질문과 맞는가
    - 검색 결과 수가 실제 결과와 맞는가
    - 검색된 상품이 사용자 질문에 맞는가
    - 최종 답변이 검색된 상품을 근거로 작성되었는가
    - 멀티턴에서 이전 대화 조건이 유지되었는가
4. Phoenix 결과를 phoenix_checks 객체에 OK / FAIL / PARTIAL / null로 기록
5. Phoenix 로그가 평가 행과 매칭 안 되면 `phoenix_judgement: "Phoenix 로그 연결 안 됨"`. 이때는 Phoenix 근거로 판정 보정하지 않음
6. 최종 판정은 LLM 1차 + Phoenix 보정 결과를 종합

### 원인명 매핑 (root_cause 출력에 사용할 한국어 표시명)

| 내부 분류 | 출력 문자열 |
|---|---|
| Mapping Issue | 로그 연결 문제 |
| Tool Selection Issue | 검색 도구 선택 문제 |
| Search Parameter Issue | 검색 조건 문제 |
| Zero Result Issue | 검색 결과 0건 |
| Retrieval Issue | 검색 결과 부적합 |
| Response Grounding Issue | 답변 근거 불일치 |
| Response Generation Issue | 답변 생성 문제 |
| Context Retention Issue | 이전 대화 조건 누락 |
| Performance Issue | 응답 지연/타임아웃 |
| Query Understanding Issue | 검색 조건 문제 |
| 없음 | 없음 |

## 평가 단계 (요약)

### 싱글턴
Step 0. CoT reasoning (≥ 20자)
Step 1. segment_tags 추출 (명시된 속성만)
Step 2. 상위 30개 상품 relevance_score 부여
Step 2-K. 상위 3개 Top-K 집중 검사
Step 3. A~E 항목 평가 + 보조 지표 (answer_length_check, keyword_relevance_check)
Step 4. Comp 계산
Step 5. issue_types 분류
Step 6. is_judge_unstable 판정 (7개 조건 중 2개 이상)
Step 7. Score 계산 및 final_judgement
Step 8. test_priority 분류 (1~4단계)
Step 9. 31위 이후 → unevaluated_products로 노출

### 멀티턴 추가
Step 3-M. Ctx 점수
Step 4-M. 드리프트 감지

### 점수 공식

```
싱글턴: Score = Rel × 0.40 + Acc × 0.35 + Comp × 0.25
멀티턴: Score = Rel × 0.35 + Acc × 0.30 + Ctx_final × 0.20 + Comp × 0.15
```

Turn 1은 Ctx_final이 null → 싱글턴 공식 적용.

### relevance_score 기준 (0~4)

| score | label | 기준 |
|---|---|---|
| 4 | 적합 | 쿼리 핵심 상품군 + 주요 조건 모두 부합, Top-K 노출 적합 |
| 3 | 적합 | 핵심 상품군 명확, 일부 부가 조건 약하지만 추천 가능 |
| 2 | 부분 적합 | 넓은 카테고리는 맞으나 세부 상품군·스타일 어긋남 |
| 1 | 부적합 | 같은 패션 카테고리이나 직접성 낮음 |
| 0 | 부적합 | 다른 대분류, 오검색, 무관 결과 |

### 평가 항목 수치 변환

| 항목 | 값 | 변환 |
|---|---|---|
| A (쿼리 의도) | PASS / PARTIAL / FAIL | 1.00 / 0.70 / 0.30 |
| B (텍스트 품질) | GOOD / ACCEPTABLE / POOR | 1.00 / 0.70 / 0.30 |
| C (관련성) | C_avg_relevance (0~1) 기준으로 HIGH(≥0.70) / MEDIUM / LOW(<0.40) |
| D (노이즈) | 비율 기준 LOW(<10%) / MEDIUM / HIGH(>30%) |
| E (다양성) | GOOD / ACCEPTABLE / POOR | 1.00 / 0.70 / 0.30 |

```
Rel  = (A × 0.5) + (C_avg_relevance × 0.3) + ((1 - 노이즈비율) × 0.2)
Acc  = B
Comp = Step 4 계산값  (상품 0건이면 0)
```

### 최종 판정

```
Fail       : Score < 0.65 OR Acc < 0.50 OR Comp < 0.50 OR 상품 0건
Hard Pass  : Score ≥ 0.85 AND Acc ≥ 0.85 AND Comp ≥ 0.85 (Top-K bad 아닐 때)
Conditional Pass : 그 외 기준 충족
```

is_outlier 자동 true 조건:
- Acc 0.50~0.84 구간
- top_3_acc_avg < 0.50

human_review는 is_outlier일 때 자동 true.

### 보조 지표 (점수 미반영)

**answer_length_check** (글자 수, 공백 포함)

| 판정 | 한국어 | 일본어 | 영어 |
|---|---|---|---|
| 충분 | > 150자 | > 100자 | > 200자 |
| 보통 | 50~150 | 35~100 | 80~200 |
| 부족 | ≤ 50 | ≤ 35 | ≤ 80 |

**keyword_relevance_check** — 일치 / 부분 일치 / 불일치 / 해당없음

### product_count = 0 분류

- JSON `tools_used = ["search_products"]` → `검색 결과 없음`
- JSON `tools_used = []` → `역질문/상품 미반환`
- JSON 매칭 실패 시 answer_text fallback

## 검증 체크리스트 (data.json 출력 직전)

### 1. 구조

- 최상위에 `meta`, `kpi`, `queries` 3개 키가 모두 있는가?
- `queries` 배열의 각 요소가 위 스키마를 따르는가?
- 단일 `data.json` 파일만 출력했는가? (HTML / CSS / JS 미생성)

### 2. KPI 일관성

- `kpi.verdict_distribution`의 합이 `meta.total_queries`와 일치하는가?
- `counter_question_count`와 `no_result_count`가 `queries[].zero_result_type`과 일치하는가?

### 3. 평가 정확성

- 상위 30개 상품에만 relevance_score를 부여했는가?
- 31위 이후가 `unevaluated_products`에 원본 그대로 들어갔는가?
- `relevance_score ≥ 3` 상품의 description / exposure_reason / reason이 생략되고 `comment_skipped: true`인가?
- `final_judgement = Pass` 케이스의 A_reason ~ E_reason, issue_detail, priority_reason, summary 전체가 생략됐는가?
- 한국어 / 일본어 / 영어 동의어 교차 매칭을 적용했는가?
- `유해` 라벨을 사용하지 않았는가?
- product_count = 0이 `역질문/상품 미반환`과 `검색 결과 없음`으로 구분됐는가?
- 가격은 selling_price 숫자값 + currency 코드로 보존됐는가? (통화 기호 없이)

### 4. Phoenix 통합

- LLM Warning / Fail 케이스에 `phoenix_checks`가 모두 채워졌는가?
- Phoenix 로그가 매칭 안 된 경우 `phoenix_judgement: "Phoenix 로그 연결 안 됨"`이고 판정 보정을 적용하지 않았는가?
- `root_cause`가 원인명 매핑표의 한국어 출력 문자열로 작성됐는가?

### 5. 출력

- 최종 산출물은 단일 `data.json` 파일인가?
- 외부 서버 / API 호출 없이 정적 JSON으로 완결되는가?
